# Changelog

All notable changes to IRDoc are documented in this file.

The format follows [Keep a Changelog](https://keepachangelog.com/en/1.0.0/).
IRDoc uses [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

The current pre-release version is tracked in [`VERSION`](VERSION).

---

## [Unreleased]

### Fixed

- **SSO role mappings now take effect.** Previously a mapping was only used the first time someone signed in, so anyone whose account already existed stayed an Analyst whatever the mapping said. Now:
  - Mappings are applied on every sign-in, and each role change is recorded in the audit log as `user.role_changed` (via SSO).
  - A mapping can match an Entra group Object ID, an app role, or a user's own Object ID.
  - If several match, the most privileged role wins.
  - Users with no matching mapping keep their current role, including one set by hand.
  - SSO never demotes the organization's last admin.
  - If mappings are configured but the sign-in token carries no groups (Groups not enabled under App Registration → Token configuration, or the user is in too many groups for Entra to list them), the backend log says so. (#172)
- **Lead Analyst on report covers is the incident's assignee.** It used to show whoever generated the first report, and regenerated versions, including the copies pushed to SharePoint, kept that name. Assigning an incident now updates the next regenerated report. Unassigned incidents still show the user who generated the report. The "Generated by" footer is unchanged. (#173)

- **Saving organization settings works again.** Changing the organization name, or anything else on Admin → Organization settings, failed with "Failed to save settings" because of how an empty logo URL was validated, and a logo URL could never be saved at all. An empty logo URL now clears the logo. The name can't be blank (surrounding spaces are trimmed), the accent colour must be a `#rrggbb` value, and the logo must be an http(s) URL. When saving fails, the message now says why. (#167, #170)

- **Incident template slugs are unique and can be edited.** The slug is how the inbound webhook picks a template (`"template": "<slug>"`).
  - Two templates in the same organization could share a slug, and the webhook then failed with a server error. Upgrading renames the extra copies: the oldest template keeps the slug and the others get a short suffix (for example `phish-2f9c1a7b`).
  - A new or edited slug must not already be used by another template of the organization or by a built-in template (`409`). It must be lowercase letters and digits separated by single hyphens (`422`). The error shows next to the Slug field.
  - Changing a template's slug used to be ignored without any error; now it is saved. The editor warns that API callers using the old slug will stop matching.
  - Copies of a template are named `<slug>-copy`, `<slug>-copy-2`, … instead of a random suffix. (#168, #169)
- **Security: the webhook only uses templates of the caller's own organization.** Given a slug that existed only in another organization, the inbound webhook used that organization's template and copied its tasks into the new incident. It now considers only the caller's organization's templates and the built-in ones, and skips hidden templates. (#168)

- **Security: session cookies are marked Secure on HTTPS installs.** `COOKIE_SECURE` was never passed to the containers, so setting it in `docker/.env` did nothing, and installs served over HTTPS sent session cookies without the `Secure` flag. It is now passed through. Left empty, it is on whenever `BASE_URL` starts with `https://`, which also covers installs behind a TLS-terminating load balancer. The installer writes `COOKIE_SECURE=true` for HTTPS installs. Set it to `false` only for a deliberately plain-HTTP setup. (#157)

### Changed

- **Startup says why it can't reach the database.** The backend, worker and beat containers used to print "Waiting for PostgreSQL..." forever, hiding the reason. They now print the reason while PostgreSQL or Redis are still starting. When retrying can't help, such as a wrong password in `DATABASE_URL` / `REDIS_URL` or a missing database, they stop at once with a message saying what to fix. They give up after 5 minutes (`WAIT_FOR_SERVICES_TIMEOUT`). Passwords are never printed. A password containing a quote no longer breaks the check. (#159)
- **Each database and Redis password is set in one place.** `docker/.env` used to hold every password twice: in `DB_PASSWORD` and again inside `DATABASE_URL` (the same for Redis). Changing only one of them left the backend unable to sign in. Docker Compose now builds `DATABASE_URL` and `REDIS_URL` from `DB_PASSWORD` and `REDIS_PASSWORD`. The installer no longer writes the URLs, and `.env.example` recommends hex passwords (`openssl rand -hex 24`), which need no escaping. Existing `.env` files keep working: a `DATABASE_URL` or `REDIS_URL` that is set still wins, which is also how to point IRDoc at an external server. (#158)
- **Webhook: an unknown template slug is rejected.** `POST /api/v1/external/incidents` with a `template` that doesn't match any visible template now returns `422 Unknown template '<slug>'`. It used to create a blank incident without saying so. Send `"template": "blank"`, or leave `template` out, for a blank incident. (#168)
- **Template API: unknown fields are rejected.** `POST`/`PUT /api/v1/templates/incident` return `422` for fields they don't know, instead of ignoring them. (#169)

## [0.1.11-alpha] - 2026-11-09

### Added

- **Use the ticket number as the incident number.** The inbound webhook (`POST /api/v1/external/incidents`) accepts an optional `incident_number`, so ticket 123456 in your service desk becomes `INC-2026-123456` in IRDoc. It must be digits only (up to 21) and is padded to 4 digits like generated numbers (`42` → `INC-2026-0042`). It can be sent as a string or a JSON number. If that number already exists this year, the request is rejected with `409` and nothing is created; the response links the existing incident. Incidents created in IRDoc keep their automatic numbers, which now skip any number already used by the webhook. It is separate from `external_ref`: send that too if you also want the external-ref badge. (#156)

## [0.1.10-alpha] - 2026-11-07

### Added

- **Incident Source.** Every incident now records what triggered the investigation:
  - User Reported / Requested
  - SIEM Alert
  - EDR / XDR Alert
  - Threat Hunting (IOC / IOA)
  - Threat Intelligence
  - Network Security Alert (IDS/IPS, NDR, Firewall)
  - Email Security / Phishing Report
  - Cloud Security Alert
  - External Notification
  - Other

  Source is required when creating an incident, and closing an incident asks for it if it's missing (the API returns `422 source_required`, or `disposition_and_source_required` when the Outcome is missing too). It shows as a chip in the incident header, where it can be changed in any status including closed, on the Summary page, on report covers and in the AI assistant's context. Changes are recorded in the audit log as `incident.source_changed`. Incidents created before upgrading have no source and show "Not recorded". The incidents list has a "Not recorded" source filter to find them, and marks them with a "NO SOURCE" chip. Incidents from the inbound webhook get "SIEM Alert" unless the request sends `source`. (#147)
- **Evidence tab.** A read-only Evidence Register in the incident workspace lists every file collected for the incident: where it came from (the timeline entry, with a link to it, or the incident itself), type, size, SHA-256, who uploaded it and when, and the assets linked to its entry. Files whose SHA-256 matches a hash IOC are marked "MATCHES IOC". Filter by name or hash, source and type, hide screenshots, sort any column, and export the filtered list to CSV (recorded in the audit log as `evidence.exported`). Images, PDFs and plain-text files can be previewed; text is always shown as plain text. An IOCs view lists the incident's IOCs with their matching files. (#150)
- **SFTP and SMB backup destinations.** Admin → Backups can now copy each backup to an SFTP server or to an SMB 3 file share, configured separately from Admin → Storage so backups can live away from the evidence they protect. SFTP requires you to confirm and pin the server's host key, and refuses any other key afterwards. SMB requires SMB 3 and encrypts the transfer by default. Passwords and private keys are stored encrypted and never shown again. A failed upload marks the backup as failed and keeps the local copy. Retention also deletes old backups at the destination, touching only IRDoc's own backup files. (#151)
- **Backup tools** in the backend container: `python -m app.cli.backup decrypt` decrypts a backup, `rekey` re-encrypts older backups with the new backup key, and `verify` rechecks every stored attachment against the SHA-256 recorded at upload. (#149)

### Changed

- **Backups have their own encryption key**, `BACKUP_ENCRYPTION_KEY` in `docker/.env`, instead of a key derived from `SECRET_KEY`. Changing `SECRET_KEY` no longer makes backups unreadable. Each backup records the key it was made with, and Admin → Backups shows that key's fingerprint. New installs from the installer wizard get a key, and `upgrade.sh` adds one to existing installs (the wizard's upgrade flow doesn't, so add it by hand there). Without it, backups keep using the `SECRET_KEY`-derived key and the Backups page shows a warning. Backups made before 0.1.10 still restore with the `SECRET_KEY` they were made with; `BACKUP_LEGACY_SECRET_KEYS` lists older `SECRET_KEY` values. (#149)
- **API: creating an incident requires `source`.** `POST /api/v1/incidents` without it returns `422`. The inbound webhook is unchanged. (#147)
- **Error messages stay on screen** until you close them, instead of disappearing after 4 seconds. Warnings stay 6 seconds. At most five messages show at once, and repeated messages aren't stacked. (#139)
- **Text files keep their type.** `.txt`, `.log`, `.csv` and `.json` uploads are now stored as text, so they can be previewed. Files uploaded before stay as they are. (#150)

### Fixed

- **Backups with the Cloud destination could report success without uploading anything** when no cloud storage was configured, ignored which storage backend was active, and with a local storage backend put backups inside later backups. A Cloud backup now fails with a clear error unless an S3, Azure Blob or GCS backend is active. (#151)
- **The automatic hash check after an upload looked in the wrong storage.** It always read from the backend set by `STORAGE_BACKEND`, not the one configured in Admin → Storage, so with S3, Azure Blob or GCS it logged "file not found" instead of checking the file. It now reads each file from the backend it was stored on. (#149)

### Security

- **Dependencies updated for new advisories:** pyasn1 0.6.5 in the backend.

## [0.1.9-alpha] - 2026-10-29

### Changed

- **Failed uploads say why.** When an attachment fails to upload, the message now gives the reason, for example "file too large for the server or a proxy in front of it (HTTP 413)", instead of only "failed". This applies when adding and when editing an entry. (#139)
- **Report template builder: choose the cover page fields.** The Cover Page block has a new "Fields to show" picker: Severity, Status, Disposition, Affected Users, Lead Analyst, Opened At and Generated At. (#140)
- **The Reports tab title** now matches the other incident tabs: the tab's icon next to the title, in the same font. (#144)
- **External ticket links must be web addresses.** The inbound webhook (`POST /api/v1/external/incidents`) and external references now only accept an `external_url` starting with `http://` or `https://`. Anything else is rejected with `422`. Existing links that aren't web addresses are shown as plain text instead of as a link.
- **The backend image no longer contains pip.** Nothing installs Python packages while IRDoc runs. pip carried its own copies of several libraries that security scanners kept flagging. If you used `docker exec … pip` for troubleshooting, use `python -c "import importlib.metadata as m; print(m.version('package'))"` instead.

### Fixed

- **The incidents list and the incident page were blank** (a black page, with `TypeError: Cannot read properties of undefined (reading 'external_source')` in the browser console) as soon as any incident had an external ticket reference. This affected every incident created through the inbound webhook / an API key with an external reference, and blanked the incidents list for everyone in the organisation. (#145)
- **Attachments didn't show after adding an entry.** The entry appeared without its files until you refreshed the page or edited and saved the entry, and the edit dialog showed no attachments. The files were saved correctly; the list was refreshed before they had finished uploading. (#138)
- **PDF previews didn't load** ("refused to connect"). IRDoc told the browser never to show its pages inside a frame, including your own uploaded files. Stored files may now be framed by IRDoc itself; everything else still can't be. The preview also has an "Open in new tab" link. (#137)
- **Reports for closed incidents left out the final disposition** when none had been recorded, which is the case for incidents closed before 0.1.8. They now show "Not recorded". The Base Template's stat row includes the disposition. Custom templates show it on the cover by default, and older templates can add it with the new cover field picker. (#140)
- **Base Template reports were listed as "pdf"** in the report history. They now read "Base Template", and reports whose template has been deleted read "Deleted template". (#141)
- **Changing a report template's colour or company name lost the unsaved layout.** Those settings save right away, and the save reloaded the template over your unsaved blocks. Changing the colour and the company name in quick succession could also lose the colour change. (#142)

### Security

- **Stored ticket links could hold `javascript:` URLs.** Anyone with an API key could set an external ticket link that ran script when clicked. IRDoc's content security policy already blocked this in current browsers; the API now rejects such links and the UI never makes them clickable.
- **Dependencies updated for new advisories:** Mako 1.4.2 and tornado 6.6 in the backend, plus pip 26.2.2 during the image build (its bundled certifi), after which pip is removed.

## [0.1.8-alpha] - 2026-10-27

### Added

- **Session timeouts.** You are now signed out after 60 minutes without activity, and must sign in again 12 hours after signing in, however active you are. Before, a session renewed itself indefinitely, so you could stay signed in for days. Admins can change both limits for the organisation in Org Settings → Sessions; `SESSION_IDLE_TIMEOUT_MINUTES` and `SESSION_MAX_HOURS` set the server defaults. You get a warning a minute before an inactivity sign-out. Everyone has to sign in once after upgrading. (#123)
- **Final disposition.** Closing an incident now asks how the investigation ended:
  - True Positive - Remediated / Contained
  - True Positive - Accepted Risk
  - True Positive - Third Party Handled
  - False Positive - Benign
  - False Positive - Tuning Required
  - Unknown - Inconclusive

  An incident can't be closed without one. The API returns `422 disposition_required`. The disposition shows as a second badge under the status in the incidents list, next to the status in the incident header (where you can change it), as "Outcome" on the Summary page, and on generated reports. A new "Disposition" stat is available for report templates. Reopening an incident keeps its disposition. Changes are recorded in the audit log. Incidents closed before upgrading have no disposition. (#124)
- **Incidents list: pages.** The list loads one page at a time: 25 incidents by default, or 50 or 100. Below the list are "Showing 26 to 50 of 132", previous/next and page numbers. Filtering, searching and paging happen on the server, so totals and pages stay correct. Changing the filter, search or page size goes back to page 1. The page, filter, search and sort are kept in the URL, so refreshing or sharing the link opens the same view, and "back" from an incident returns to it. The API's default page size is now 25 and its maximum 100. An unknown `status` filter now returns an error instead of an empty list. (#127)
- **Incidents list: sorting.** Click a column header to sort by Severity, ID, Title, Created, Owner or Status. Click again to reverse. Severity sorts by level and Status by workflow order (Open, Contained, Monitoring, Closed), across all pages. The first click on Severity puts the most severe first, and on Created the newest first. Unassigned incidents sort last by Owner. The default is newest first. (#128)
- **Rename incidents.** Click the title in the incident header (or the pencil next to it) to rename the incident. Press Enter to save or Escape to cancel. Renames are recorded in the audit log with the old and new title. Analysts and above can rename. Blank titles are rejected. (#125)
- **Sign out everywhere.** Settings → Profile → Sessions ends your sessions on every browser and device. Changing your password now also signs out your other sessions. (#123)

### Changed

- **Your own nginx config now lives in `docker/nginx/local/nginx.conf`.** The frontend image ships its own default config (plain HTTP), and installs that need something else, such as HTTPS or custom certificate paths, put a full config in `docker/nginx/local/nginx.conf`. That folder is not tracked by git, so editing it no longer makes `git pull` fail on upgrade. The installer wizard writes its generated config there. `docker/nginx/nginx.conf` is no longer used. If you edited it, `upgrade.sh` and the wizard move your edits to `local/nginx.conf` and put the original back. The demo HTTPS config moved to `docker/nginx/examples/demo-https.conf`. (#114)
- **Incidents list columns line up.** Every row uses the same columns, under a header row: severity, ID, title with its age below, owner, status, actions. Badges have a fixed width. Long titles and owner names are cut off with "…", and the full text shows on hover. On narrow screens the owner shows as an avatar only, and on phones each row stacks. (#126)
- **`upgrade.sh` keeps `VERSION` in `docker/.env` up to date.** It now updates `VERSION` in `docker/.env` to the version you upgrade to, so a later `docker compose up -d` doesn't go back to the old images. It also warns when the checked-out release doesn't match the version you are upgrading to. (#131)

### Fixed

- **Frontend kept restarting on a fresh install** with `open() "/etc/nginx/snippets/irdoc-security-headers.conf" failed`. This happened when the checked-out config was newer than the frontend image, for example with an old `VERSION` in a reused `docker/.env` or an outdated cached `latest` image. The default config now comes from the image itself, so the two always match. (#131)
- **Signing in with Entra ID set a session cookie without the `Secure` flag**, even when `COOKIE_SECURE=true`. It now follows `COOKIE_SECURE` like every other sign-in. (#123)

### Security

- **Dependencies updated for new security advisories:** Pillow 13.0.0, Brotli 1.2.1, certifi 2026.10.23, dnspython 2.9.0 and opentelemetry-api 1.45.1 in the backend, and follow-redirects 1.16.2 in the frontend. None of them are used directly; they come in through WeasyPrint and other libraries.

## [0.1.6-alpha] - 2026-10-11

### Changed

- **Severities renamed to Critical, High, Medium and Low.** SEV-1 is now CRITICAL (a new, darker red), SEV-2 is HIGH (red), SEV-3 is MEDIUM (yellow) and SEV-4 is LOW (blue). This applies across the incident list, the incident workspace, the summary page, the overview dashboard, Teams notifications and generated reports, where the severity now reads "Critical" instead of "SEV-1 (Critical)". Existing incidents are converted automatically when you upgrade. The API now returns `critical`, `high`, `medium` and `low` instead of `sev1`-`sev4`; it still accepts the old values when creating, updating or filtering incidents, and on the external incident webhook, so existing integrations keep working. Audit log entries and reports generated before the upgrade keep the old names. (#109)
- **New icon set.** The colour emoji icons are replaced by single-colour Font Awesome 6 icons that follow the dark/light theme. Text symbols used as icons (such as ✓, ⚠ and ▼) are replaced too. Integrations show their own logo: VirusTotal, SharePoint, Shodan and AbuseIPDB. Some icons that stood for two things are now split, for example Storage and Server, Settings and Org Settings, and Workstation and Laptop.
- **IRDoc logo on the sign-in screens.** Login, first-run setup, invite sign-up and the required two-factor setup now show the IRDoc logo (light or dark to match the theme) instead of a shield or an "IR" tile.
- **Plain hyphens instead of em dashes.** Labels, messages, empty table cells, generated reports, Slack messages and seeded templates use "-" instead of "—" or "–". AI-written text is converted the same way before it is saved. Text already stored, such as the audit log, existing reports and existing templates, is not changed.
- **Security headers come from the frontend image.** The Content-Security-Policy and the other security headers (X-Frame-Options, X-Content-Type-Options, Referrer-Policy, Permissions-Policy) now ship in the frontend image instead of being written into `docker/nginx/nginx.conf`, so upgrades keep them current. HSTS stays in `nginx.conf`, because it depends on the HTTPS mode. Installs using the plain-HTTP default `nginx.conf` now also get the CSP and Permissions-Policy headers. (#57)
- **Upgrades update an old `nginx.conf`.** `upgrade.sh` and the installer wizard now switch an existing `nginx.conf` to the shared security headers. Only the header lines change; certificate paths and any other edits are kept, and the original is saved next to it as `nginx.conf.bak-<date>`. If nginx rejects the updated file, the backup is put back automatically. Wizard snapshots now include `nginx.conf`, so a rollback restores it too. (#57)

### Removed

- **`icon` field in `GET /api/v1/integrations`.** It held a frontend image filename and was only used by the IRDoc UI, which now picks integration icons itself.

### Fixed

- **"Pinned" marker missing its icon in generated reports** when the backend ran in Docker: the icon was read from the frontend source folder, which isn't in the backend image. It is now part of the report template.
- **IRDoc logo looked smaller in the light theme** than in the dark theme, in the left navigation and on the sign-in screens. Both logo files now have the same square canvas and padding, so the logo is the same size in both themes (and slightly larger than before). (#102)
- **Uploaded or pasted images showed as broken in the UI on upgraded installs** (logo preview in the report template editor, screenshots pasted into rich text). Installs created before 0.1.2 kept an outdated Content-Security-Policy in `nginx.conf` that blocked these previews, because upgrades never updated that file. Upgrading now fixes it (see Changed). Generated reports were not affected. (#57)
- **Installer wizard upgrades failed at "Running database migrations"**: the step used the container name instead of the compose service name, and would have run the migrations with the old image. (#105)
- **Timeline tab re-rendered in a loop** while it was open ("Maximum update depth exceeded" in the browser console), wasting CPU even when no entry was being edited. (#101)

## [0.1.5-alpha] - 2026-10-09

### Fixed

- **Report templates (and incident templates) listed twice.** On a fresh install the backend, worker and beat containers seed the database at the same moment. Two of them could both find the template tables empty and each insert the full set of system templates. The seed step now takes a database lock, so only one container seeds. Upgrading removes the extra copies; incidents, tasks, reports and sync policies that used a removed copy are moved to the one kept. A system template stays visible if any copy of it was visible. Custom templates are not changed. (#93)

## [0.1.4-alpha] - 2026-10-08

### Added

- **SharePoint: save reports into an existing folder.** A new optional **Folder in Library** field, and **SharePoint Site URL** now also accepts the browser URL of the target folder (library view `…/AllItems.aspx?id=…`, folder path, or "Copy link" sharing link). IRDoc then takes the library and folder from the URL. Libraries are matched by display name (`Documents`, `Documenten`) or URL name (`Shared Documents`, `Gedeelde documenten`); before, only the display name matched, so a URL name created a new, empty library. Existing folders are reused and missing ones are created. (#86)
- **SharePoint filename placeholders** `{severity}`, `{status}`, `{date}` and `{version}`, alongside `{incident_ref}`, `{incident_title}` and `{template_name}`. `{date}` was already documented but fell back to the default name. Characters SharePoint rejects are replaced with `-`, and `.pdf` is added when missing. Each integration field now shows a short hint under it. (#87)

### Changed

- **`upgrade.sh` refuses source-built installs.** On an install started with plain `docker compose up` (built from source, port 3000), it used to switch silently to the published-image stack (ports 80/443, files in `docker/storage/`). It now stops with instructions instead. It also waits for the backend health check before reporting. (#82)
- **Real version reported.** The release version is baked into the backend image, so `upgrade.sh`, the version badge and the update check show e.g. `0.1.4-alpha` instead of `1.0.0` or the image tag `latest`. (#82)

### Fixed

- **`Permission denied: '/app/storage/reports'` on a fresh Docker install.** Docker creates the bind-mounted `docker/storage` and `docker/backups` owned by root, and the app runs as uid 999. The backend, worker and beat containers now take ownership of both directories at startup, then drop to the unprivileged user, so existing installs are fixed by upgrading. (#80)
- **Cloning an incident template failed** ("Failed to clone template"): the clone endpoint the Incident Templates page calls didn't exist. Clones are named "<name> (Copy)" and are fully editable. (#81)
- **Generated Reports table showed "pdf" as the template**; it now shows the report template's name. (#88)
- **Login said "Invalid credentials" for every failure**, including a backend that was still starting, the login rate limit, or an unreachable server. Those now get their own messages. (#82)

### Security

- **Dependency updates:** urllib3 2.7.0 → 2.8.0 (PYSEC-2026-4175/4176/4177) and tornado 6.5.8 → 6.5.9 (GHSA-chx6-46f5-w4vp, GHSA-c2m8-h5v5-343r, GHSA-3hv7-mjh2-fv65).
- **python-jose CVE-2026-85394** (algorithm confusion, no fixed release yet) is not exploitable in IRDoc: every token check restricts the algorithm (HS256 with the server secret, RS256-only for Entra ID). It's temporarily excluded from the CI audit until python-jose is replaced.

## [0.1.3-alpha] - 2026-09-26

### Added

- **Version badge** at the bottom of the left nav and in **Settings → About IRDoc**. It's grey when up to date, and yellow (the SEV-2 colour) with the newer version and a link to the release when an update exists. (#67)

### Changed

- **Summary tab Severity/Status cards** are about 30% shorter and always one line. The value is 18px, medium weight, and the value and top border are coloured by the actual severity/status (same colours as the chips elsewhere). (#66)
- **AI features greyed out when Local AI (Ollama) is disabled**: the AI Summary and AI Recommendations cards (and their Generate buttons), the AI Strategy Summary block in the report template builder, and the per-template AI toggle stay visible but disabled, with a hint pointing to Integrations → Local AI. A new `GET /ai/status` endpoint exposes the on/off state to every role. The generate endpoints now return 409 when AI is disabled instead of queueing a task that can't run. (#68)

### Fixed

- **Actions To Do rendered badly in PDF reports**: each task's checkbox sat on its own line above the text, and completed tasks showed an empty box. Tiptap keeps the completion state only in `li[data-checked]` (the `<input>` never has `checked`), and the report stylesheet had no task-list rules. Task items now render inline, with a drawn checkbox that is filled and ticked for completed tasks, whose text is struck through. (#70)
- **Reports regenerated 1 minute after the last change**: the default auto-regeneration delay is now **10 minutes**, so a burst of edits yields one new version. The defaults offered when configuring Local AI and SharePoint are also 10 minutes; delays an admin has already saved are unchanged. (#71)
- **Incident search ignored the reference**: search matched only the title, so `INC-2026-0002` (or `0002`) found nothing. Search now matches the title or the reference, case-insensitively, and `%`/`_` are matched literally. (#64)
- **Couldn't set a time on a new timeline entry**: a 1-second timer rewrote the Time field while the form was focused, overwriting whatever was typed. The form now has a live mode: date and time follow the clock until you edit either one, then stay pinned. A **Now** button returns to live mode, and a live-mode entry is stamped with the actual submit time. (#65)
- **Update check never reported new versions**: it used GitHub's `/releases/latest`, which excludes pre-releases. Every IRDoc release is a pre-release, so the call always returned 404. It now lists releases and picks the highest by PEP 440 order, and flags an update only when that version is strictly newer than the running one (a newer or `dev` build no longer gets told to "update"). The installer wizard's update notice had the same bug and is fixed too. (#67)
- **Reports not regenerated after incident changes** — auto-regeneration only existed as two integration-specific pipelines (AI, and SharePoint-without-AI), so on an install with neither enabled, editing an incident never produced a new report version. Even where it existed: AI orgs only regenerated templates flagged `ai_auto_generate`; AI + SharePoint orgs never regenerated or pushed unflagged templates; and the SharePoint debounce fired only if the 10-second beat scan happened to land in the key's last ~2 seconds, so most triggers were silently dropped. Replaced with a single debounced pipeline (`report_regen_service` + `auto_regenerate_reports`): once any report has been generated for an incident, every later change to it (fields, timeline, IOCs, tasks, assets, asset links, attachments) queues one new version of each template already used, including the base report. AI narrative and SharePoint push are applied per version when enabled. The debounce is now a trailing-edge token check on the scheduled task instead of a beat scan. Timeline deletes, IOC edits/deletes, task deletes, attachments and asset links now trigger regeneration too. (#58)
- **Report version stuck at v1 for non-AI reports** — `version_number` was only computed inside `generate_report`'s AI branch. Versions are now assigned per (incident, template) when the report is created, for manual and automatic reports alike, and the reports table shows the version for every report. (#58)
- **Report template Section block empty for every field except Executive Summary**: the field list pointed at `incident.metadata.*` keys that nothing in the app writes (Root Cause, Affected Data, Regulatory Notes, Preventive Actions). Analyst Notes read `metadata.notes`, but the Summary tab saves Notes to the `notes` column. AI Recommendations were never copied onto the report payload. The Section block now offers exactly the incident Summary tab fields (Executive Summary, Notes, Lessons Learned, To-do), resolved from one backend field map (`report_renderer/fields.py`). Saved templates using `incident.metadata.notes` now render Notes. Other removed fields render a "no longer supported" notice instead of silently showing no data. To-do task lists render as a checklist in PDFs. (#60)
- **Text Block was a duplicate of Section**: it showed the same field list but could only resolve 4 of the 9 fields. A Text Block now holds rich text written into the template (disclaimers, guidance, sign-off) and appears the same in every report. Existing field-bound text blocks keep rendering, and the builder offers a one-click "Convert to Section". (#61)
- **Evidence Register block only configurable by label**: added **Show SHA-256 hashes** and **Show uploader** toggles. The uploader column was read from config but never rendered; it now shows the uploader's name. (#62)
### Internal

- **CI: lock file out of sync**: regenerated `requirements.lock.txt` after adding `packaging` as a direct requirement (#67).

## [0.1.2-alpha] - 2026-09-22

### Fixed

- **Incident tabs and left-nav frozen after the first click** — `react-router-dom` v7's `<BrowserRouter>` now wraps every location update in `React.startTransition()` by default. Under React 18, that transition-wrapped update to `<Routes>` could be starved by other synchronous re-renders in the tree (zustand/WebSocket-driven state on the incident workspace page) and never commit, even though `history.pushState`/`replaceState` had already changed the URL — so a tab or nav click changed the address bar but left the previous screen on-screen, and every navigation afterwards (any tab, any nav item) stayed stuck until a full page reload. Fixed by opting out with `useTransitions={false}`, restoring synchronous route updates. (#48)
- **`beat` container always reporting unhealthy** — its healthcheck shells out to `pgrep`, which isn't part of the `python:3.12-slim-bookworm` base image (no `procps`); it has failed with `pgrep: not found` (exit 127) every 30s since the healthcheck was added, even though the `celery beat` process itself was running fine. Added `procps` to `backend/Dockerfile`. (#49)
- **Report generation failing with `'function' object has no attribute '_fail_on_errors'` whenever the report template had a logo** — WeasyPrint 70.0 (picked up in the CVE-2026-55073 patch bump from 62.3) removed `weasyprint.urls.default_url_fetcher` in favour of a `URLFetcher` class, and now reads `url_fetcher._fail_on_errors` whenever a fetch raises. The renderer's data-URI-only fetcher was still a plain function calling the removed API, so it raised `ImportError` on every call and WeasyPrint then blew up reading `_fail_on_errors` off a function. It only surfaced once a document actually referenced a resource — i.e. only for templates carrying an uploaded logo, which is stored as a base64 `data:` URI; logo-less reports never called the fetcher and rendered fine. Replaced with a `URLFetcher(allowed_protocols=("data",))` instance, which keeps the same SSRF / local-file-disclosure guard natively. (#50)
- **Strict CSP blocking the SPA's own assets** — the nginx policy (`default-src 'self'; script-src 'self'; object-src 'none'; frame-ancestors 'none'`) set no `style-src`, `img-src`, `font-src` or `connect-src`, so all four fell back to `'self'` and the browser blocked the webfont stylesheet, the editor's injected `<style>` tag, and every `data:`/`blob:` preview — including the logo preview on the report-template editor. The policy now declares `style-src 'self' 'unsafe-inline'` (TipTap/ProseMirror injects a `<style>` tag at runtime and nginx serves `index.html` statically, so a nonce isn't available), `img-src 'self' data: blob:`, `font-src 'self'` and `base-uri 'self'`, while `script-src` stays `'self'` with no `'unsafe-inline'`/`'unsafe-eval'`. Fixed in both the installer's nginx generator (`installer/core/ssl.py`, which is what real installs render) and the static `docker/nginx/nginx.demo-https.conf`. (#51)
- **New timeline entries saved off by the browser's UTC offset** — the "add entry" form built `occurred_at` as a naive `${date}T${time}` string with no timezone offset and sent it as-is. The column is `timestamptz` under a UTC database session, so the local wall-clock time the form displayed (e.g. `19:57:03`) was stored as if it were already UTC, then correctly converted back to local for display — silently re-adding the offset a second time (e.g. `22:57:03` in UTC+3) on every read. The entry-edit form already converted correctly via `new Date(...).toISOString()`; the add-entry form now matches it. (#52)

### Changed

- **Webfonts are now self-hosted** instead of being loaded from `fonts.googleapis.com`. IRDoc is deployed on-prem and frequently air-gapped, where the external stylesheet silently fell back to system fonts; self-hosting also removes a third-party origin from the CSP and stops leaking viewer IPs to Google. Adds `@fontsource/syne` and `@fontsource/jetbrains-mono`; every Google subset is still declared with its `unicode-range`, so browsers download only the glyph ranges a page actually uses (Vite is now told never to inline font files — its 4KB default was embedding the small Greek/Cyrillic/Vietnamese subsets into the main stylesheet as `data:` URIs, which shipped them to every visitor and tripped `font-src` as well).

### Internal

- **CI's backend test job was intermittently failing with `out of shared memory` / `increase max_locks_per_transaction`** — the test suite's `setup_db` fixture drops and recreates the full ~28-table schema before every single test; measured directly, one cycle holds ~361 locks in one transaction, which reproducibly exhausted Postgres's default shared lock-table budget partway through a run and cascaded into failing every later test too. Raised `max_locks_per_transaction` to 1024 for CI's `postgres:16-alpine` service (via `POSTGRES_INITDB_ARGS`, the only way to set a postmaster-context setting on a service container). (#54)
- **A second, unrelated CI failure: `RuntimeError: ... attached to a different loop`** — `test_mfa_admin.py` and `test_mfa_verify.py` were marked `@pytest.mark.anyio` instead of `@pytest.mark.asyncio`, the only two files in the suite doing so; this ran them on a different event loop than `pytest-asyncio`'s shared one, corrupting the test suite's shared DB connection pool and taking two unrelated tests down with it. (#54)
- **`npm audit` in CI was failing on vitest/vite/esbuild advisories** that only affect devDependencies never shipped in the production bundle. Scoped the audit to `--omit=dev`, matching how the backend's `pip-audit` step already handles an accepted, unfixable finding rather than disabling the check outright. (#54)

## [0.1.1-alpha] - 2026-09-18

### Fixed

- **Fresh Docker installs crash-looping on first run** — `docker-compose.prod.yml` set `AI_BACKEND` to an always-injected empty string by default; the backend's `Literal["anthropic","openai","ollama"]` setting rejects that at startup, crash-looping `backend`, `worker`, and `beat` together (they share one entrypoint that imports settings before starting anything). `AI_BACKEND` now defaults to `anthropic`, matching the app's own default.
- **First-run setup screen not appearing** — `GET /auth/setup-status` returned a bare `{"setup_complete": ...}` instead of the `{"data": {...}}` envelope every other endpoint uses. The frontend's response parsing threw against the unexpected shape and failed silently, so a fresh install with zero users rendered a normal login form with no way to create the first admin account.
- `docker-compose.prod.yml` now passes `ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, and `OLLAMA_BASE_URL` through to the backend — setting these in `docker/.env` had no effect before this release.
- Removed the misleading `EMAIL_BACKEND` line from `.env.example`; it isn't read by the app — SMTP is configured per-organization from the admin UI after login, not via environment variables.

### Security

- Patched fixable CVEs in base container images and tuned Trivy CI scanning (`ignore-unfixed`), cutting code-scanning noise from ~971 alerts down to the handful that are actually actionable.

### Added

- `demo.irdoc.io` seed data and a 6-hourly automated reset script for the public demo environment.

### Changed

- The frontend Docker image is no longer published for `linux/arm64` — a Vite/Rollup arm64 native dependency deadlocks installing under this project's CI QEMU emulation. The image is static, nginx-served content and runs fine on an arm64 host under its own amd64 emulation if needed. The backend image is unaffected and still ships both `linux/amd64` and `linux/arm64`.

### Internal

- Release image tagging now strips a leading `v` from the git tag, so `docker-compose.prod.yml`'s `VERSION` value actually matches the published image tag.
- Added a 30-minute timeout to the Docker build-and-push CI job, so a hung build step fails within 30 minutes instead of silently running for up to GitHub's 6-hour default.
